Before anyone joins about 10 minutes

The lab must already be warm when the call starts. Do not start containers on screen — a progress bar in front of a CIO is ten minutes you do not get back. 

  1. .\run.ps1 up

    NetBox, Postgres, Redis, the lab runner and the scoped Docker proxy. Wait until {{netbox}} answers and you can log in as admin / admin. 

  2. .\run.ps1 workbench-lab

    Eight nodes: six cEOS switches plus the two Philips servers, dual-homed across each MLAG pair. It also turns off ZeroTouch and configures the server trunk on Ethernet5 of every leaf. Allow a minute for the switches to settle. 

  3. .\run.ps1 eapi

    Do not skip this. A freshly deployed switch answers nothing on eAPI, and every page that reads the fabric will show six unreachable devices. This is the step that is easiest to forget because nothing tells you it is missing.

    It reports ok per switch when the switch answers through NetBox — the same path the plugin uses, so a pass here means the pages will work. 

  4. .\run.ps1 itsm

    Zammad, on {{itsm}}. This is the one command that is easy to get wrong if you type it by hand, so use the wrapper. It does three things in order:

    1. Starts the stack with both compose files.
    2. Waits for the database schema to exist.
    3. Creates the admin, the group, the API token and the settings, then proves the token works from inside NetBox.

    Both compose files, in that order. Zammad lives in its own compose file, so --profile itsm against the main file starts nothing; and starting it with the ITSM file alone puts Zammad on a different Docker network from NetBox, where the plugin cannot reach it. The ticket tab then says ITSM is not configured while Zammad is plainly running at {{itsm}}. First start takes several minutes because it runs its migrations.

    Good: the last lines say me 200 admin@example.com, setup_done True, and ITSM ready.

    "ITSM is not configured" on the Tickets tab means NetBox cannot resolve zammad-nginx — the two stacks are on different networks. Re-run .\run.ps1 itsm; do not try to fix it by hand.

    Log in as admin@example.com / admin. If you are not showing the ticket story, skip this — the demo works without it, and the page says so rather than showing an empty list. 

  5. .\run.ps1 workbench-check

    Good: the last line says READY.

    Not good: NOT READY. It names the failing step and the command that fixes it. Fix it and run it again. Never open the meeting on a NOT READY. 

  6. .\run.ps1 workbench-live

    This breaks a switch on purpose and puts it back, so it is the only check that proves the demo will work rather than that the page loads. Idempotent — run it as often as you like.

    Good: PASS — 14 steps verified against real switches. 

  7. .\run.ps1 deck-show
.\run.ps1 workbench

    Leave the workbench on the Fabric tab. Test screen-share with both windows, then close everything you do not need — including notifications.

The demo, click by click 15 minutes

Everything here is the workbench page at {{workbench}}, five tabs. No terminal on screen. The buttons apply real changes to real switches.

  1. Do: open the Fabric tab. Six cards, all green. Point at one and read the software version row — you come back to it in step 5.

    Everything you see here comes from two places: NetBox, which is what we said the network should be, and the switches themselves, which is what it is. Green means they agree. This is the whole idea — one place that knows what your network is meant to look like, and can prove it.

    Good: all compliant in the top right, six devices, six green cards.

    Red cards: see If something breaks. Do not debug it in front of the room.

  2. Do: Day-two change tab. Switch leaf-01, VLAN 150. Click Preview change.

    Nothing has happened yet. Read the diff aloud: one VLAN created, and the allow-list added on Ethernet5.

    This is the answer to the thing you said in our last conversation. Today that is a change request, a maintenance window, and someone typing on four switches and hoping they got all of them. Here it is one object in the source of truth, and the tools work out the rest.

    Good: a small diff — vlan 150, a name, and one or two switchport trunk allowed vlan lines.

  3. Do: type your name in Approved by. Click Approve and apply.

    The approve control only appears after a preview, and it will not send anything without a name. Say that out loud — it is the CISO's question answered before she asks it.

    Good: "Applied by your name" and a green result.

    "Nothing was sent": the switch already matched. Usually means a previous run left VLAN 150 in place. Fine to talk over, or reset and restart.

  4. Do: back to Fabric. leaf-01 is green; the other three leaves show the change as pending.

    The other leaves still need it. That is deliberate: I approved one switch, not the estate. When you want all of them, that is a policy decision you make, not a side effect of a button.

    This is the most important honesty beat in the demo. Do not skip it, and do not be tempted to click through all four leaves quickly to make it look tidy.

  5. Do: still on Day-two change, click Inject drift. Then Fabric — leaf-01 is red with the exact port and the exact missing VLAN. Then back and Remediate drift, type your name, approve.

    Nobody told the system. It found it.

    That change was made on a real switch, outside the tool. That is what makes this a demonstration rather than a mock-up.

    Good: red card with a specific finding, then green after the approval.

  6. Do: Lifecycle tab. Compliance and operating system, per device, on one page.

    Same engine, the fleet view. Which devices match what we said, and what are they running. This is where your CVE problem stops being a spreadsheet exercise — when you set a target version in NetBox, this becomes your upgrade worklist.

    Ties to their Q1 2027 refresh. A refresh done without a model just replaces old drift with new drift.

  7. Do: Two vendors tab. Same intent, same gate: an Arista switch and an FRRouting router.

    You said the vendor label on the box shouldn't matter. This is the same source of truth, the same approval, the same record, driving two different vendors. Arista is fully read, diffed and applied here. FRR is read and diffed, and applied through its own reload path — I'm telling you which parts are done rather than showing you a slide.

    Do not cut the last half-sentence. It matters more than the demo. Overclaiming here is how you lose a CTO who already knows the difference.

  8. Do: Audit trail tab, newest first, with the approver on every entry. Open a "before and after" to show the switch's own configuration on both sides.

    Every one of those changes — including the one I broke on purpose — is in an append-only record with my name on it and the switch's configuration before and after. And a demo reset does not clear it.

    Good: at least two applied changes, both naming you.

The same story inside NetBox 5 min, optional

Use this if somebody asks "does this live in our tool, or do we have to go and live in another one?" Everything below is NetBox itself at {{netbox}}, logged in as admin / admin. The whole loop is {{netbox}}/plugins/ops/.

  1. Do: Network Ops → Devices. Six cards. Then open any device and use NetBox's own Render Config tab.

    That is 187 lines of Arista configuration rendered from the source of truth by NetBox itself, with no extra tool in the path. It is the answer to "is this a product of yours or a product we own?".

  2. Do: Live config tab, pick a switch.

    Read live over eAPI as the page loads. Secrets are redacted. Useful right after a change: reload and the new stanza is there.

  3. Do, in order, on the Day-two change tab:

    1. Step 1 — Preview the change. Captures the switch's config as the before-state and shows the diff.
    2. Step 2 — Open the ticket. A real Zammad ticket with the diff in the body.
    3. Step 3 — type your name, select that ticket in the dropdown, then Approve & push.

    Good: step 3 shows the switch's own config before and after, the words compliant with intent, and the ticket moved to open and then closed. All three are read back, not asserted.

    Selecting the ticket is what makes the state changes happen. Without it the push still works — it just has no ticket to move, which is a quieter demo than you want.

  4. Do: ITSM tickets tab, click Open on a ticket.

    It goes to Zammad at {{itsm}} — a real ticket in a real system, in the state the change left it.

    Dead link: the ITSM stack is not running, or itsm_public_url is wrong. See If something breaks.

  5. Do: Container labs tab. Eight nodes listed.

    You do not need to press Deploy during the meeting. The point is that it is there, and that it is scoped: NetBox reaches Docker through a proxy that exposes container state and start/stop and nothing else. No socket, no exec, no root on the host. That sentence is worth more to this audience than the button.

The five questions to expect

"Are you replacing ServiceNow?"
No. It stays your change system of record. NetBox holds configuration intent — what a device should be, per port. Different question, different data. You saw the ticket land in an ITSM system in exactly the state your process would leave it.
"Are you replacing Infoblox?"
No. Infoblox stays the IPAM authority. We integrate. Nobody is asking you to move yours.
"How long until we see value?"
Six weeks to 80% of the estate modeled and one real change automated. The last 20% is the hard part and we won't pretend otherwise.
"What about our firewalls?"
Palo Alto fits the same pattern — intent, approval, audit. Not demoed today; 90 minutes is 90 minutes.
"Who owns the data?"
You do. In your NetBox, your Git, your change control.

Two they may not ask, but you should raise

"When does anything act on its own?"
Not until you approve the gates. Read-only first, then assisted — the system proposes, a human approves — and automated only inside a change path you have signed off. That is deliberate, and it is the reason a CISO can say yes.
"We're already mid-refresh. Does this wait?"
No — it runs alongside. Your refresh starts Q1 2027, and a refresh done without a model just replaces old drift with new drift.

Things not to say

  • "Single pane of glass." Nobody in that room wants another one.
  • "Zero downtime" about anything we have not proven. That is a switching-platform property, not ours, and the CTO knows the difference.
  • A CLI. Stay out of a terminal in this room.
  • "It just works." Say what it does and what it doesn't.

If something breaks

Fix at most one thing live, and only if it takes seconds. Otherwise say what happened, move to the deck, and come back. Do not debug a container in front of a CIO.

SymptomDo this
"Could not read intended state" .\run.ps1 up, wait about 90 seconds, then Refresh.
Every device says "did not answer" eAPI is off. .\run.ps1 eapi. This is the most likely single failure.
A device is missing from the page .\run.ps1 status, then .\run.ps1 workbench-lab.
Nothing changes when you approve Check the audit tab. If it says nothing was sent, the device already matched — that is a no-op, not a failure.
A preview fails .\run.ps1 apply to get the switches back onto the rendered config.
Tickets tab says ITSM is not configured NetBox cannot reach zammad-nginx: the stacks are on different networks. Re-run .\run.ps1 itsm, which passes both compose files.
Zammad shows "Set up a new system" The setup step has not run. python scripts\zammad_setup.py finishes it and keeps any existing data.
Tickets tab: 401 on a valid token The token in plugins.py is stale. python scripts\zammad_setup.py rewrites it and restarts NetBox.
Ticket creation fails with 403 The Zammad user has no group access. Roles alone are not enough; the setup script sets it. Re-run it.
Ticket links are dead Zammad is down, or itsm_public_url does not point at {{itsm}}.
NetBox asks you to log in That is correct. admin / admin. It is meant to be closed — it drives switches.
You want to start over .\run.ps1 workbench-reset. Puts the fabric back and keeps the audit.

The deck stands alone. If the lab dies mid-demo, say so, show .\run.ps1 workbench-walk output if it helps, and move to the six-week slide.

Reset and run it again

.\run.ps1 workbench-reset

Then start at the Fabric tab. The audit log keeps both runs, which is usually a good thing to show — it is the record of two full change cycles.

A reset applies real changes to real switches and is itself recorded, with demo reset as the approver. It never clears the record. A reset returns the lab to its starting state; it does not rewrite what happened.

What this is not

  • It does not replace ServiceNow. It reads and writes configuration intent.
  • It does not replace Infoblox. It is not an IPAM authority.
  • It does not touch firewalls today.
  • The trunk layer is a lab overlay — the shipped fabric has no server-facing ports, so the demo adds one real trunk per leaf.
  • It is a lab. Not a customer network, and it says so in the footer.
